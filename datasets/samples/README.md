# Sample datasets

Four small, **synthetic** datasets used by the teaching modules. Every file here is generated by
[`scripts/make_sample_datasets.py`](../../scripts/make_sample_datasets.py) and committed, so a
learner can start a lesson without downloading anything.

```bash
python scripts/make_sample_datasets.py           # regenerate
python scripts/make_sample_datasets.py --check   # verify the committed files match the generator
```

## Provenance and licence

| Question | Answer |
| --- | --- |
| Where did this come from? | Generated by the script above. Nothing is scraped or third-party. |
| Does it describe real people? | **No.** No personal data, no real customers, no real properties. |
| Licence | The repository licence — see [`LICENSE`](../../LICENSE). |
| Reproducible? | Byte-for-byte. The generator uses a hand-written integer generator, not `random`, and avoids the platform maths library entirely. |

> **⚠️ Synthetic data has synthetic limits.** These files are built for teaching mechanics —
> loading, cleaning, joining, fitting. They contain none of the messiness that makes real data hard:
> no shifting definitions, no upstream schema changes, no genuine label ambiguity. Never draw a
> conclusion about the world from them, and never use a result obtained here as evidence that an
> approach works on real data.

**The data is deliberately imperfect.** Missing values, inconsistent casing, duplicate rows, a dead
sensor and an impossible reading are all placed on purpose, at fixed positions, so that the modules
can point at them. Clean data teaches nothing about cleaning.

## `reviews.csv` — text classification

Short product/film reviews with sentiment labels. **62 rows**, 5 columns.

| Column | Type | Notes |
| --- | --- | --- |
| `review_id` | string | `r001`…`r060`. **Not unique** — see below. |
| `text` | string | Free text. Contains commas and embedded quotes. |
| `label` | string | `positive` / `negative` |
| `rating` | integer | 1–5, **may be empty** |
| `source` | string | `web`, `mobile`, `kiosk` |

**Deliberate faults**

| Fault | Count | Why it is here |
| --- | --- | --- |
| Rows with an empty `rating` | 4 | Missing-value handling |
| Labels in the wrong case (`POSITIVE`, `NEGATIVE`) | 3 | Normalise before counting classes |
| Text with leading/trailing whitespace | 2 | `.strip()` at the boundary |
| Exact duplicate rows | 2 | 62 rows, 60 unique `review_id` values |
| Commas and `"` inside `text` | many | Why you never split CSV on commas |

Class balance **as stored** is 36 `positive` / 23 `negative` / 2 `POSITIVE` / 1 `NEGATIVE` — which
looks like four classes until you normalise the case. That is the point.

Used by: [Topic 10](../../01-python-foundations/10-json-csv-and-apis.md),
[Topic 12](../../01-python-foundations/README.md).

## `sensor_readings.csv` — numeric time series

Temperature and humidity from three sensors over a simulated 80 hours. **240 rows**, 4 columns.

| Column | Type | Notes |
| --- | --- | --- |
| `timestamp` | ISO 8601 string | Not a datetime until you parse it |
| `sensor_id` | string | `s-01`, `s-02`, `s-03` |
| `temperature_c` | float | Degrees Celsius, **may be empty** |
| `humidity_pct` | float | Percent, **may be empty** |

**Deliberate faults**

| Fault | Detail |
| --- | --- |
| Missing readings | 2 empty `temperature_c` (s-01), 2 empty `humidity_pct` (s-03) |
| **Dead sensor** | `s-02` reports exactly `21.50` / `48.0` for 6 consecutive steps |
| **Impossible outlier** | one reading of `148.00` °C on `s-03` |

Observed temperature range is **10.71 to 148.00 °C**. The upper end is the fault — a naive
`max()` or `mean()` finds it immediately, which is the lesson. The stuck sensor is nastier: the
values are perfectly plausible, and only their *variance* gives it away.

Used by: [Topic 11 NumPy](../../01-python-foundations/README.md),
[Topic 12 pandas](../../01-python-foundations/README.md).

## `housing.csv` — regression with known ground truth

Property prices generated from a **known linear relationship** plus noise. **150 rows**, 6 columns.

| Column | Type | Range |
| --- | --- | --- |
| `property_id` | string | `p001`…`p150` |
| `area_sqm` | float | 45.2 – 209.5 |
| `bedrooms` | integer | 1 – 5 |
| `age_years` | integer | 0 – 60 |
| `distance_km` | float | distance to the centre |
| `price_thousands` | float | 113.4 – 774.0, mean 391.4 |

**The generating process is public**, which makes this dataset unusually useful for learning:

```text
price = 60.0
      + 3.2 × area_sqm
      + 12.0 × bedrooms
      − 1.4 × age_years
      − 4.5 × distance_km
      + noise (σ = 18.0)
```

So when you fit a linear regression in
[Topic 14](../../01-python-foundations/README.md), you can compare the learned coefficients against
the true ones — and see how close 150 noisy samples get you. Almost no real dataset lets you do
that.

> This also makes it a poor test of *modelling skill*: the relationship really is linear and
> additive, so a linear model is guaranteed to work. Real data offers no such guarantee.

## `customers.jsonl` — nested records

One JSON object per line. **40 records**, with optional and nested fields.

```json
{"contact": {"country": "SE"}, "customer_id": "c001", "plan": "pro", "region": "us-east",
 "tags": ["support-heavy"], "usage": {"requests_last_30d": 31703, "storage_gb": 10.74}}
```

| Field | Type | Notes |
| --- | --- | --- |
| `customer_id` | string | `c001`…`c040` |
| `plan` | string | `free` (13), `pro` (17), `enterprise` (10) |
| `region` | string | `eu-west`, `us-east`, `ap-south`, `eu-north` |
| `usage.requests_last_30d` | integer | nested |
| `usage.storage_gb` | float | nested |
| `tags` | list of strings | **empty in 16 records** |
| `contact.country` | string | **absent entirely in 10 records** |

The missing `contact` block is the point: `record["contact"]["country"]` raises `KeyError` on a
quarter of the file, while `record.get("contact", {}).get("country")` does not.

Used by: [Topic 10](../../01-python-foundations/10-json-csv-and-apis.md).
